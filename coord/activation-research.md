## 0. The problem

The fleet agents only really run when their owner messages personally. Otherwise just one subagent watches Messenger and replies for show, and the repo sits empty. On 13/11 the fleet lost ~2 hours to exactly this hole, and the 19:40 order (Muse/Tuan) calls it SUPER serious: solve it starting now, first repo evidence before 20:00, repo checked at 20:00 and 20:30 — no commit/PR counts as sitting idle.

This memo answers two questions: (1) why do agents idle without owner pings, and (2) what actually fixes it. Every factual claim traces to a primary source cited inline. Anything marked not verified is marked as such and is not load-bearing.

## 2. Root causes (5, research agent — each with evidence)

### RC1 — No liveness rule covers the coordinator. The runbook hardens workers, not the coordinator.
FLEET-MODE §16.1 covers a WORKER dying mid-loop (JSON checkpoint after every stage, resume from the last checkpoint, never restart); §16.2 adds `stop_reason=agent_died`. Neither names the coordinator. §12 lists 11 failure modes; none is "coordinator goes silent / coordinator dies". The closest ("context drift / stale state") is about agents building against changed state, and its guard ("one-line status every 30 min") is a reporting habit, not a liveness check with a reader. The Deputy role exists on paper (rehearsal task file: "Deputy: Migga") but has NO trigger condition. Consequence: when the coordinator died at ~12:37, no rule any other agent could invoke; the loss was bounded only by the user noticing at 14:29.

### RC2 — Agents are turn-based: they only run when invoked. There is no wake-up except an owner ping (and, since 14:44, the group-watch hook).
`coord/migga.md` records the limitation twice, in the agents' own words: the 04:25 coordinator entry and the 10:12 day-shift entry both state "turn-based subagent, cannot poll the group every 2 minutes; group checked at milestones". This matches Anthropic ("Agents begin their work with either a command from, or interactive discussion with, the human user", "Building effective agents", via the research briefs). The 14:44 hook only watches the Optimus group for @mentions and wakes the parent; it does not watch the repo, does not watch coordinator silence, and does not wake a worker or a Deputy. Consequence: a coordinator that stops mid-shift is indistinguishable from a coordinator with nothing to do — until a human pings or a deadline passes.

### RC3 — Silence is undetectable by design: the stuck-agent rule requires the stuck agent to report itself.
FLEET-MODE §15.2 (15-minute rule): "Stuck for more than 15 minutes: report the blocker in the group and switch to another task." A dead, crashed, or stalled agent cannot report itself. §15.1 says "silence is invisible" and "if nobody can see it, it did not happen" — but its enforcement is again self-reporting plus the coordinator watching both channels every 15 minutes. The coordinator is the watcher; nobody watches the coordinator (RC1). Consequence: the fleet's only silence detector on 13/11 was the user confronting the parent at 14:29.

### RC4 — The coordinator is a single point of failure by design, and the runbook concentrates authority in it.
§15.1: "Call the coordinator, not the humans. The coordinator routes." §15.4: merges are sequential and the coordinator orders them. The coordinator is the only integrator, the only router, and the only merge-orderer. Anthropic: "Synchronous execution creates bottlenecks... the entire system can be blocked while waiting for a single subagent to finish searching" — the mirror image is what happened on 13/11: the whole fleet blocked while waiting for a silent coordinator. Consequence: coordinator silence does not degrade the fleet gracefully; it halts it. On build day the humans will be pitching, not watching the repo, so the halt would last until a demo deadline forces someone to look.

### RC5 — Work is batched to the end of a shift instead of being made visible as it lands.
§15.1 already orders "push after every finished piece, in small atomic commits" and §15.2 says "§7's 'commit every ~30 minutes' is a floor, not the rhythm". The 14:44 order shows the opposite practice: pushes deferred, QC held back, work reported at end of shift. Two mechanisms make batching rational: §15.3's "focused re-read" rewards holding a PR until it is "ready", and §15.4's merge serialisation makes the agent wait for the coordinator's merge order. Asymmetry the D74 draft does not mention: §15.4 forbids force-push and forbids touching `coord/run-log.jsonl` except via the coordinator — an agent whose coordinator is silent cannot even record its own status in the run log. Consequence: even when agents ARE working, the repo and the group show nothing, so "working" and "dead" look identical from outside.

## 3. Candidate solutions (5, research agent — each with honest limits)

All costs $0.00: no new paid service, account, key, or dependency.

### S1 — Heartbeat + Deputy takeover (the D74 draft). ADOPT as the core fix, with the gaps below closed.
While a run is live, the coordinator writes a heartbeat line every 15 minutes (timestamp, current stage, next action, blockers). Silence >20 minutes (one missed heartbeat + 5 min grace) = coordinator presumed dead. The Deputy (named in the task file at run start) takes over: announces in the group, re-reads the latest checkpoints + run log, resumes from the last checkpoint — never restarts — or declares a stop with `stop_reason=coordinator_died`. Fixes RC1, RC4 (bounds loss from ~2 h to ~20 min), part of RC3. Cost: one log line per 15 min. Limits: (1) heartbeat is self-reported — a coordinator alive but stuck passes the check; must be paired with §16.1 checkpoints (a heartbeat with no checkpoint advance for two rounds is also a failure). (2) The Deputy is also a turn-based subagent — nothing in D74 wakes the Deputy; without S2/S3 the trigger exists on paper and nobody pulls it. (3) False-takeover risk on long legitimate operations (a 25-min fix round per §16.5, a slow build, a long CI wait); the claim must be atomic (first takeover entry in the run log wins). (4) The Deputy needs the same repo write/push and group-post rights as the coordinator, verified BEFORE the run.

### S2 — Scheduled self-checks: a cron that probes liveness and wakes the parent when the run goes stale.
A runtime cron (same mechanism as `optimus-watch`) every 10–15 minutes during a live run reads three facts — last heartbeat timestamp, last commit to the run's branches, last run-log entry — and wakes the parent if any is staler than its threshold (heartbeat >20 min, no commit >45 min while live). The cron only detects and wakes; it does no repo work itself. Fixes RC2's "who wakes the Deputy" gap in S1. It is the ONLY solution in this list that fires when NOTHING happens. Cost: $0.00 (runtime cron + small shell probe; no model call unless it wakes someone). Limits: (1) detection is not recovery — if the parent is also idle, the chain breaks again. (2) False positives on legitimately quiet periods (waiting on a human, on CI, deliberate pause); thresholds must be run-phase-aware. (3) The cron itself can fail silently — mitigate by having the cron write its own probe line to a log, and keeping the probe trivially simple.

### S3 — Event-hook wake-ups: extend the `optimus-watch` pattern from the group to the repo.
Keep the group hook (polls every 120 s, wakes the parent on @mentions) and add repo-event hooks of the same shape: a new PR, a new commit on a watched branch, a new `coord/<name>.md` entry wakes the coordinator (or the parent) within minutes. Fixes RC2 for the event half — the missed 14:10/14:15 tags are exactly the class of event a hook catches. Cost: $0.00 (same runtime-hook mechanism already running). Limits: (1) hooks fire on events, never on silence — a fleet where nothing happens triggers nothing; S3 without S2 leaves the 12:37–14:29 hole exactly as it was. (2) Wake storms: needs dedup and spacing (wake at most once per 5 min per trigger class), or it breaks the standing group-message discipline (max 10/hour, ≥5 min apart). (3) Single-machine fragility: the hook runs on the parent's runtime; if that runtime restarts or the hook dies, the watch dies with it — mitigate with a liveness line the hook writes on each poll, checked by S2's cron.

### S4 — Standing-order escalation + coordinator rotation.
(a) Escalation: any fleet agent observing coordinator silence >20 min MAY declare itself Deputy in the group and the run log, resume from the last checkpoint, and continue — no permission needed. (b) Rotation: no coordinator instance holds the run for more than ~2 hours without a handoff carrying §16.1 `STATE:` + `NEXT:` lines and the latest checkpoint. Fixes RC1, RC4, part of RC5. Cost: $0.00. Limits: (1) a rule without a watcher is unenforced (RC3 again) — without S1's heartbeat and S2's cron, S4 is the 12:47 non-stop order again. (2) Rotation costs context: every handoff loses something; the 13/11 record shows three overnight coordinators (00:33, 00:50, 04:25) each re-verifying state from scratch, each handoff a chance to drop work. (3) Two-claimant race — needs the atomic claim from S1. ALSO: rotation contradicts the runbooks (BUFFET §1: "Rotation only between runs, never mid-run"; FLEET §1: "Muse, FIXED for the whole run") — Expert 1 rejects rotation as a solution to this hole.

### S5 — Enforce what is already ordered: push-first + per-piece reporting, with a repo-side detector.
The 14:44 order (push the moment a piece is finished, then QC on the pushed branch; report every push/PR/fix in the group the moment it lands) plus the missing detector: the coordinator (or S2's cron) checks at each 15-minute watch (§15.1) that every agent with an open assignment has a commit or a status line within the last 45 minutes, and names the silent one in the group. Fixes RC5 and part of RC3. Cost: $0.00. Limits: (1) it re-states §15.1/§15.2, which already said this and did not prevent 13/11 — on its own it changes nothing; it only works as the reporting half of S1+S2. (2) It can be gamed (trivial commits to look alive) — the check must be on checkpoint advance (§16.1), not commit count. (3) It puts the detector back on the coordinator — the per-agent check must be runnable by ANY agent (or by the S2 cron), not only by the coordinator.

**Research recommendation:** no single solution closes the hole. Minimum viable combination is S1 + S2 (trigger + waker), plus S3/S5; S4 optional. Do NOT adopt any of these as words alone — each needs its detector named in the same decision, or it repeats the 12:47 order.

## 4. Council verdicts (independent experts — each read the primary sources itself)

### Expert 1 — coordination/systems (verdict 19:47 ICT)
**Key finding: succession ALREADY EXISTS in BUFFET §1 but did not apply on 13/11.** BUFFET-MODE.md §1 already defines Deputy succession in full. But `coord/BOARD.md` states in each handoff section that "Buffet-run rules (BUFFET-MODE.md §5 leases, 15-min poll, deputy succession) do NOT apply to the handoff — the handoff is milestone-driven". The 13/11 work ran under handoff mode. And on build day, FLEET-MODE §7.9 imports BUFFET §5 (leases, polls, merge protocol) but does NOT list §1 succession among the imported rules. So as of `origin/main` 4fba0b6, there is no succession rule in force for build day at all. D74 is therefore not inventing succession — it is (belatedly) porting it into FLEET-MODE. The question is not whether to have succession, but what clock and what fencing it carries.
**Three defects in D74 as drafted:** (1) No fencing — it can create the BUFFET F19 failure (two coordinators); BUFFET §1 has two-phase takeover (post `COORDINATOR TAKEOVER`, wait one full 15-min pull cycle, `COORDINATOR ALIVE` voids it) plus a term number (`coordinator-term: N+1`) on every board write. (2) No pending-work condition — false positives on legitimate idle; BUFFET §1 requires BOTH pending work unprocessed for the window AND no coordinator commit in that window ("An idle coordinator with an empty queue is idle, not stale: no pending work means no takeover, whatever the clock says"). (3) Wrong vocabulary + ambiguous heartbeat channel — §16.2's vocabulary is `gates_green / max_rounds / coordinator_stop / agent_died`; `coordinator_died` does not exist there (use `agent_died` unless §16.2 is formally amended); and the heartbeat must be one line in the coordinator's own `coord/<name>.md` (the BUFFET `Last seen` pattern), pushed every 15 min — never a branch commit touching `coord/run-log.jsonl` (§15.3 forbids it, and an unpushed heartbeat is invisible: "Liveness = pushes, full stop").
**Pick:** PRIMARY — D74 amended (15-min pushed heartbeat, 20-min staleness test with pending-work condition, takeover under BUFFET §1 two-phase fencing + term numbers; sensor = Deputy-side 15-min poll). FALLBACK — (b)+(c) driving the already-written BUFFET §1 succession at its 60-min clock; if both deputies stale, the run pauses. **Strongest failure:** the Deputy and its sensor share the failure domain, and the heartbeat measures pulse not progress — mitigated by the pending-work half of the test, backup Deputy on a different live machine, and the run-pauses rule; residual: nothing watches the watcher. **Honest limit (stated by Expert 1, §6):** this verdict does NOT fix the overnight runtime hole in full — if an agent's runtime only wakes on an owner message, no repo rule can wake it. The heartbeat + Deputy mechanism fixes the *coordination* hole given live runtimes; the *runtime* hole is a separate problem.

### Expert 2 — multi-agent systems research (verdict ~19:46 ICT)
**Research basis:** Anthropic (resume-from-checkpoint, harness-enforced caps not prompting), Google (driver owns the loop, not the agent session — "Make the loop a dumb deterministic driver... not a long-lived agent session"), OpenAI (resume is a runtime capability; "own the loop yourself"), DeepSeek (externally-triggered restart protocol; "a failed launch is not retried on its own — a person's message or a retry ends the hold"), LangGraph (checkpoint-per-superstep; the checkpointer, not the supervisor node, enables resume). All agree: **liveness must be checked outside the watched session.** The fleet has no such runtime — the "runtime" here is the repo + the Muse runtime's cron/hook machinery. **Honesty note:** no primary source prescribes a coordinator heartbeat or Deputy takeover as such. D74 is a legitimate *application* of the principles, not a quote. Any verdict claiming "Anthropic recommends a coordinator heartbeat" would be fabricated.
**Pick:** PRIMARY — D74 heartbeat + Deputy takeover, with the trigger enforced by a scheduled 5-min cron probe (coordinator writes a heartbeat line every 15 min; silence >20 min wakes the Deputy, who resumes from the last checkpoint or declares the stop). FALLBACK — event-hook wake-ups extended to repo activity (optimus-watch pattern for pushes/PRs); reactive only, cannot detect silence, so never the primary. REJECTED — standing-order escalation alone (already failed 13/11; prompt-only rules don't hold per Anthropic) and coordinator rotation alone (no liveness signal, handover loss, token-expensive). **Strongest failure:** a live-but-stalled coordinator can pass the timestamp check by heartbeating without progress — mitigated by mandatory stage/next/blockers fields, treating two identical heartbeats as stalled, and checking stage completions/pushes alongside heartbeats.

### D78 — Coordinator liveness: pushed heartbeat + Deputy takeover under BUFFET §1 fencing, enforced by a scheduled probe (AWARDED 2026-11-14)

**D78 claims decision number 78.** Verified free: no `D78` in `skills/frontend-kit/references/decisions.md` on main 4fba0b6 (grep count 0); max decision recorded there is D73; D74–D77 are drafts in coord files. Claim recorded here first, per the runbook rule; to be written into `decisions.md` only after Muse awards it.

**Primary solution: D74 as amended (S1 + S2 as one mechanism).** Add FLEET-MODE §16.7 (coordinator liveness) and one line in §7.9 importing BUFFET §1 succession for build day (it currently imports §5 only). No change to §16.1–§16.6, no change to the guard gate, no new script, no new dependency. Cost $0.00.

**Concrete mechanism:**
1. **Who writes what, how often.** Coordinator (fixed for the run; FLEET §1): every 15 minutes of wall-clock time while the run is live, pushes one heartbeat line in its own `coord/<name>.md` (Last-seen section): `HB <UTC> — stage: <current stage> — next: <next action> — pending: <n unprocessed items> — last-merge: <short hash or —>`. Same commit as other work when work exists; a standalone liveness commit when it does not (BUFFET §1 carve-out). Also publishes board + run log after every merge pass (§5, ≤30 min). Deputy (named at run start, NOT Mie — BUFFET §1/BOARD.md: Mie cannot post in the group; gate-tooling verified per BUFFET F29; backup Deputy also named, on a different machine): polls every 15 minutes, exempt from adaptive backoff: `git fetch origin <mainline>` + read board at remote tip + read the coordinator's heartbeat line. Workers unchanged (§15.2, §15.1, §16.1 checkpoints). One watcher, not four — four watchers would produce four competing takeovers.
2. **Enforcement leg (the missing piece in D74 as drafted).** A runtime cron (existing Muse cron machinery — the same kind already used for tonight's 19:00/19:16 debate writes) runs a deterministic shell probe every 5 minutes while a run is live: it reads the last heartbeat timestamp from the remote and compares it with wall-clock time (server-observed push time, never the coordinator's self-reported clock). No model call; a timestamp comparison only. The probe logs every check (fired or not), so a missing probe log is itself visible the next morning. The probe is disabled only by an explicit run-end entry, never by silence.
3. **What exactly triggers takeover (staleness test — BOTH must hold).** (a) Pending work exists and has been unprocessed for >20 minutes: a claim, a completion, or a slice awaiting merge; or a worker `BLOCKED` post older than 15 min with no coordinator response; or a PR awaiting merge for >30 min. The Deputy names the specific pending item and its `since` time. (b) AND no coordinator push in that window: no board pass, no merge, no heartbeat line on the remote. An idle coordinator with an empty queue is idle, not stale: no pending work means no takeover, whatever the clock says. A heartbeat line with `pending: 0` is a valid sign of life. Detection latency bounded at 20 min after the last sign of life; takeover effective ≤35 min after it (20 min test + 15 min fencing wait).
4. **What counts as idle.** Worker idle: no push for 60 min or 2× `expected-min`, whichever is shorter (BUFFET §5 lease) — coordinator marks the slice `failed`, reassignable. Coordinator idle (not stale): heartbeat current, queue empty — nothing happens. Coordinator stale: the two-condition test above.
5. **What the Deputy does, step by step.** (1) Detect on a 15-min poll (or on the probe's wake): record evidence (pending item + `since`, last coordinator commit hash + server time). (2) Post `COORDINATOR TAKEOVER <UTC> — reason: <pending work unprocessed since X> — last coordinator commit <hash> — term: <N+1>` in its own `coord/<name>.md` and push. Do not act as coordinator yet. (3) Wait one full pull cycle (15 min). If the old coordinator posts `COORDINATOR ALIVE <UTC>` in its own file and pushes inside that window, the takeover is void: post `TAKEOVER VOID — coordinator alive` and stand down. (4) After the window with no alive-signal, take ownership: write `coordinator-term: <N+1>` on the board through the merge-pass procedure (short-lived `coord/board-…` branch, merge commit — never a direct push to the mainline), and post one line in the group announcing the takeover (the one group message this procedure sends). (5) Re-read the latest `checkpoint.json` files, the run log, and the board. Resume from the last checkpoint — never restart (§16.1). Unpushed work counts as not done (§15.1); list it as lost, do not silently recreate it. Any slice with no land record on the remote mainline is unlanded and is re-trialled from the remote tip before landing. (6) Suspend own claim (`input-required`, note "deputy became coordinator; claim suspended") and reassign or re-list it. Freeze own unlanded slices: they stay `working` under the Deputy's name but the Deputy-coordinator never lands or stop-decides them; they go to the human-return packet. A Deputy who built a slice never merges it. (7) If the Deputy is itself stale, the backup Deputy runs the same procedure with the same test and the next term number. If both deputies are stale, the run **pauses**: all slices to `input-required` with the blocker named; wait for human-on-return. No third deputy, no silent continuation without a coordinator. (8) The old coordinator, on seeing a higher term, posts `STOOD-DOWN` in its own file, resumes as a worker, and must not push any local merge afterwards. A duplicate land is detected by the run log: a slice whose land is already recorded on the remote is never re-landed.

**Fallback: BUFFET §1 succession at its 60-minute clock, driven by the (b)/(c) sensor.** If the 20-minute heartbeat mechanism proves too noisy or the heartbeat channel fails, the Deputy falls back to the 60-minute pending-work staleness test with the same two-phase takeover. The fallback needs no new code — it is already on `origin/main` — and if both deputies are stale the run pauses (all slices `input-required`, wait for human-on-return). Slower (60–75 min detection latency) but less false-positive-prone and already agreed text. The event-hook layer (S3, optimus-watch pattern extended to repo activity: new PRs/commits/`coord/<name>.md` entries wake the coordinator/Deputy) is the sensor that feeds both clocks. Standing-order escalation (S4) and rotation (S4) are NOT solutions: escalation already failed on 13/11 and rotation contradicts FLEET §1 ("Muse, FIXED for the whole run") and BUFFET §1 ("Rotation only between runs, never mid-run") — keep the orders as policy, never as the mechanism. Push-first + per-piece reporting (S5) is adopted as the reporting discipline that makes the heartbeat meaningful (heartbeat + checkpoint advance, not heartbeat alone).

**Corrections to D74 adopted as conditions of this pick:** C1 fencing (BUFFET §1 two-phase takeover + term number, steps 2–4 above). C2 stop token: use `stop_reason=agent_died` on a coordinator-death stop unless §16.2 is formally amended to add `coordinator_died` — Expert 1 verified the token does not exist in §16.2; Expert 2 called it a "consistent extension", but the council follows the verified fact over the characterisation: do not cite a non-existent token as existing. C3 heartbeat channel: the coordinator's own `coord/<name>.md`, pushed — never `coord/run-log.jsonl`. C4 Deputy eligibility: not Mie, gate-tooling verified, Deputy + backup named at run start, on different machines.

**Strongest reason the primary could fail:** the heartbeat measures pulse, not progress — a coordinator alive enough to push a heartbeat every 15 min while its merge queue rots passes the timestamp check while the run is dead; and the Deputy/sensor shares the failure domain (if the Deputy's machine/runtime is also idle or dead, no poll runs, no takeover fires). Mitigations: the pending-work half of the staleness test is the progress check (a heartbeating coordinator with a rotting queue still trips condition 1); two identical heartbeats (same stage, same next) count as stalled; Deputy + backup on different machines, each gate-tooling verified before the humans leave; the sensor runs on the Deputy's machine, independent of the coordinator's; the fallback (60-min succession) and the run-pauses rule bound the worst case to a paused run, not a silently wrong one. **Residual, stated honestly:** nothing in this design watches the watcher — the Deputy's poll/probe itself has no watchdog, and that recursion terminates only at the human return. If the whole fleet's runtimes are down, no in-system mechanism can recover it; the correct outcome then is a paused run with the state in files (§16.1), not a pretended recovery.

**What this does NOT claim (honest limits):** (1) No primary source prescribes a coordinator heartbeat — D78 is an application of Anthropic/Google/OpenAI/DeepSeek/Framework principles (resume-from-checkpoint, driver owns the loop, harness-enforced caps), not a quote. (2) The 20-minute number is design judgement, not a sourced constant (BUFFET §5 admits the same for its own 10/15/30/60-minute numbers). If the first rehearsal shows false-positive takeovers, fall back to the 60-minute clock — do not improvise a new number mid-run. (3) This fixes the *coordination* hole given live runtimes; it does NOT fix the *runtime* hole — if an agent's runtime only wakes on an owner message, no repo rule can wake it. That is a separate problem for the activation work and must be stated to the humans, not assumed away. (4) D74's claim that `swarm/multi-agent-loop-research/` does not exist is now WRONG — verified via `git ls-tree origin/main`: the directory exists on main 4fba0b6 with REDTEAM/SYNTHESIS/anthropic/deepseek/frameworks briefs. The D74 proposal does not depend on that claim, but the claim must not be repeated.

## 10. Round 3 — D78 condition: progress-signal heartbeat (2026-11-13 ~20:20 ICT)

**Context:** Muse's 20:00 RECOMMENDATION conditionally approves D78 with ONE condition: the heartbeat must carry a PROGRESS signal (newest commit/PR or a "blocked: <reason>" line), not just a pulse — 2 consecutive cycles with no progress escalate to the Deputy. ### 10.1 Heartbeat line format (amended D78)

The coordinator appends one line to its own `coord/<name>.md` every 15 min and pushes it (the heartbeat commit). One line, machine-parseable, human-readable:

`HB 2026-11-13T13:00:00Z stage=<stage> next=<short next action> progress=<short hash of the newest commit or PR this run produced, or "none"> blocked=<short reason with underscores, or "none"> pending=<count of unprocessed pending items>`

Rules: `progress=` is the newest commit/PR short hash (7+ chars) the coordinator's run has produced — a NEW hash in a later heartbeat is progress. `blocked=` names the current blocker (`blocked=waiting-human-eas-login`); a reason that appears, changes, or clears is progress. Timestamps are UTC ISO8601. No spaces inside values (underscores instead).

### 10.2 The progress check (what "2 consecutive cycles with no progress" means)

A "cycle" is the interval between two consecutive heartbeat lines (nominally 15 min). A cycle is no-progress when the newer line's (progress, blocked) is identical to the older's. Escalation rules, in order:

1. **Progress** — progress hash changed, OR blocked reason appeared/changed/cleared → OK. The run is moving.
2. **Blocked-and-reported (legitimate, no escalation now)** — blocked != "none" and stable across cycles: the coordinator is stuck on a KNOWN blocker it has already reported. The Deputy and the humans can already see it in the heartbeat, so the probe does NOT escalate. The 60-min clock applies instead: if the same blocked reason persists unchanged for >=60 min from its first appearance, the Deputy intervenes (reassign the unblock, escalate to humans, or declare the slice `input-required`) under the BUFFET §1 succession rule — the probe reports this as NO-PROGRESS with reason BLOCKED-STALE-60MIN.
3. **No progress and silent (escalate)** — blocked = "none" and (progress, blocked) identical across TWO consecutive no-progress cycles (three consecutive heartbeat lines, pairwise identical, spanning >=30 min) → escalate to the Deputy. The probe exits 4 (NO-PROGRESS).
4. **One no-progress cycle only** — two identical lines (blocked=none) spanning >=15 min but no third line yet → watching, NOT escalating (exit 0, logged as NO-PROGRESS-1CYCLE). Two cycles are required; one is a warning.

Why the blocked distinction works: a reported blocker is visible state — the Deputy already knows what is stuck and why, and the 60-min clock bounds how long a reported block can sit. Silence is invisible state — the run looks alive (heartbeats arrive) while nothing moves, which is exactly the 13/11 failure mode. The progress signal turns the heartbeat from a pulse into a state report.

### 10.3 Probe changes (activation-probe.sh, amended)

New flag `--heartbeat-file <path>` (default `coord/muse.md` — the rehearsal coordinator's file; pass the coordinator's own file for other runs). The probe reads all `HB ` lines from that file at `origin/<branch>` and evaluates §10.2: last three lines for the 2-cycle check; earliest line carrying the current blocked reason for the 60-min check. Exit codes: 0 OK (progress, or blocked-reported within its 60-min allowance, or one no-progress cycle only) | 2 STALE (existing takeover condition: tip age > stale-mins AND pending work — evaluated first) | 3 ERROR (cannot read state — loud, never OK) | 4 NO-PROGRESS (escalate to Deputy: two silent no-progress cycles, or a blocked reason stable >=60 min). The log line gains `progress=<hash> blocked=<reason> hb_span_s=<seconds>`.

### 10.5 Self-attack on this amendment (honest limits)

- The progress hash is coordinator-reported: a coordinator can fake progress by pushing empty commits. The hash proves a push happened, not that the push was useful — the Deputy still judges quality; the probe only catches silence, not slop. Mitigation: the hash must be a real commit/PR on the run's branch (the Deputy can inspect it in one command), and the 2-cycle rule bounds the damage to 30 min.
- Heartbeat lines are content, not server events: a coordinator can backdate HB timestamps or rotate blocked reasons ("waiting-X" -> "waiting-Y") to reset the clocks. Each rotation counts as progress only if it names a NEW blocker with evidence (the Deputy reads the heartbeat); rotation without evidence is visible in the log and the Deputy judges it. The probe implements no forgery cross-check — that is a Deputy-side inspection, not a probe property.
- The 2-cycle rule needs three heartbeat lines: a run younger than 30 min cannot trip NO-PROGRESS even if it is dead from the start — but a young run trips STALE instead if its tip goes quiet with pending work, so the gap is covered by the other check.
- NOT tested: the probe against the real fork; the probe as a live 5-min cron; the end-to-end wake drill; other machines' hook/cron availability. Same limits as round 2, unchanged.
